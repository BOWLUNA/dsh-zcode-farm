# 排错

[English](TROUBLESHOOTING.md) | **中文**

> 下面每一条都是真实观察到的，并附上能区分各种情形的检查方法。

## 没有任何实例合格

`comfyui_farm_status` 把每一台都判为不合格。先看判定列：

| 显示的判定 | 含义 | 该改什么 |
| --- | --- | --- |
| `不可达：超时` | 端点**两次**都没能应答 | 检查隧道或 URL，不是插件的毛病 |
| `空闲显存 < 需要` | 这台装不下这个任务 | 本次把 `needVramGb` 调低 |
| `队列深 > 上限` | 前面排的任务太多 | 调高 `maxQueueDepth`，或者干脆等 |

`comfyui_farm_run` 出于同样原因拒绝启动不是 bug —— 那是过滤器在远端的显存不足发生**之前**把它拦下。

## 它选中的实例比我预想的更忙

队列深度按设计主导排序：一个排队任务扣 `queueWeight`（默认 1000）分。
所以一台空闲 33 GB、队列为空的实例，会胜过一台空闲 99 GB、但已有一个排队任务的实例。

如果你更愿意让显存最大者胜出，把 `queueWeight` 设为 `0`。
注意只有当任务大小一致、队列从不重要时，那才是正确答案。

## 派发成功了，但文件不在我看的地方

默认的文生图模板走 ComfyUI 自己的 `SaveImage` 节点，所以产出落在**那一台实例**的输出目录里 ——
对远程实例来说，那是在远端机器上。

`comfyui_farm_run` 会把它被告知的文件名与子目录返回来；用同一个 base URL 通过
`/view?filename=…&subfolder=…&type=output` 取回。

## 一台明明活着的实例被报成已下线

单次探测失败在给出结论前会重试一次，正是因为跨隧道抖动很常见：
开发机上曾出现过同一台实例一次 `>3000 毫秒` 超时、紧接着一次 `106 毫秒` 成功。

如果你看到「不可达」而那台机器明显活着，检查 `attempts` 字段 ——
两次尝试之后才给出的结论，比一次尝试后给出的更有分量。链路慢的时候调高 `probeTimeoutMs` 会有帮助。
