# 架构

[English](ARCHITECTURE.md) | **中文**

> 这个插件为什么长成这样。下面每一条决策都是对着一个**实测过的**替代方案
> 做出的，不是偏好。

## 问题的形状

一个 ComfyUI 服务**一次只执行一个工作流**。它的 `/prompt` 端点校验图、把它追加到队列、返回
`prompt_id` —— 队列由那个进程顺序消费。所以真正的并发只能来自**多开实例**，再把每个任务路由到
最早能开始的那一台。

这就是本插件存在的全部理由：只连一个端点的 Agent 看不见农场其余部分，于是它在忙卡的队列后面排着，
而旁边空闲的那张一直空转。

## 状态从哪里来

两个端点，都是只读，都是 ComfyUI 公开 HTTP API 的一部分：

| 来源 | 给出什么 | 为什么是它 |
| --- | --- | --- |
| `/system_stats` | 设备名、总显存、空闲显存、ComfyUI 版本 | 实时真相；没有会过期的记账 |
| `/queue` | 正在跑与排队中的 prompt 数量 | 真实队列，不是本地猜测 |

**刻意不用**：任何本地跟踪的「这台忙不忙」标志位。别人提交的任务 —— 另一个 Agent、一个 notebook、
一个在 ComfyUI 画布前的人 —— 对本地计数器是隐形的，而一个把忙实例报成空闲的插件，比什么都不报更糟。

## 选择：两段式，队列主导

```
1. 过滤   不可达  或  空闲显存 < needVramGb  或  队列深 > maxQueueDepth   → 出局
2. 排序   score = 空闲显存(GB) − 队列深 × queueWeight        （默认权重 1000）
```

**为什么让队列主导。** Agent 真正要问的是「哪里最快跑完」。队列空的那张立刻开始；队列更深的那张
无论显存多大都更晚开始。权重把这个说清楚了：一个排队任务扣 1000 分，所以**小而闲**胜过**大而忙**。
把 `queueWeight` 设为 `0` 就回到朴素的「显存最大者胜」—— 只有当每个任务大小一致、队列从不重要时，
那才是正确答案。

**为什么先过滤。** 把装不下的任务排序到某台上，会在远端、在等待之后，才以显存不足失败。
硬过滤则快速失败，并且说明原因。

## 探测失败会重试，而不是被当成结论

开发机上实测：同一台实例有一次超时 **>3000 毫秒**，而下一次调用只用 **106 毫秒**就返回。
跨 SSH 隧道的一次抖动不等于实例已死。

所以单次失败从不作数：探测会重试（`probeRetries`，默认 1），并把 `attempts` 一并报出。
这个区别对 Agent 可见，它能分辨「真下线」和「眨了一下」。

**同样刻意的**：当某个过滤条件淘汰了一台实例，它**原本的**理由会被保留。
一台不可达的实例即便被 GPU 型号关键字筛掉，仍然报「不可达」——
把它改标成「GPU 不匹配」会让真正的问题藏在一个听起来很合理的原因后面。

## 零运行时依赖

`fetch` 与 `AbortController` 在 Node 20+ 里就有。其余全是算术与字符串格式化。这不是为了极简而极简：

- 装好的插件与 harness 同进程运行；每多一个依赖，就多一次弄坏别人启动的机会
- 这个插件的活是跟一个 HTTP API 说话 —— 平台已经自带客户端了

## 边界

| 关注点 | 归谁 |
| --- | --- |
| 工作流库、技能包、画布、资产面板 | `dsh-comfyui` |
| N 个端点里该谁接这个任务 | **本插件** |

两者互相独立：装配行 id 不同（`comfyui` vs `comfyui-farm`）、不共享代码，装任一个都不需要另一个。
